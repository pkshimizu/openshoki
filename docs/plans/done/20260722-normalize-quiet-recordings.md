# 極端に小さい音量の録音を停止後に自動正規化する（Meet 録音でマイクが無音に聞こえる問題）

- 作成日: 2026-07-22
- ステータス: ドラフト

## 概要

Google Meet などのオンラインミーティングを録音すると、マイク側の MP3 が「再生しても無音」に
なることがある。実データの解析で、**音声は録れているがレベルが約 40dB 低い**（ピーク
-35dBFS / RMS -61dBFS）ことが判明した。原因は会議アプリ（ブラウザ）の自動ゲイン調整（AGC）が
マイクの OS 入力ボリュームを下げるためと推定される。対策として、録音停止後のバックグラウンド
処理で「極端に小さい音源」をゲイン上限付きで正規化して保存し直す。

## 背景・前提（コンテキスト）

- **実データの解析結果**（`/Users/kenji/Documents/openshoki/20260722-093032`）:
  - `mic.mp3`: 1ch 48kHz・59 分・ピーク **-35.1 dBFS**・RMS **-61.0 dBFS** → 体感無音。
    ただし whisper は（内部正規化を経て）会話を正しく文字起こしできており、**音声情報は
    存在する**。
  - `system.mp3`: ピーク -0.4 dBFS・RMS -22.0 dBFS → 正常。
  - よって「録音経路の故障」ではなく「入力レベルが極端に低い」問題。
- **原因の推定**: macOS では、ブラウザ（Meet）の getUserMedia の autoGainControl が
  **マイクデバイスの OS 入力ボリュームそのもの**を調整する。会議アプリがゲインを下げた状態で、
  openshoki は同じデバイスを素のレベルで共有して録るため、極小音量になる。openshoki 側から
  デバイスゲインを触るのは会議アプリと奪い合いになるため行わない（会議品質を壊さない）。
- 録音停止後は既にバックグラウンド後処理がある: `MixWorker`（両音源の `mix.mp3` 生成）と
  `TranscribeWorker`（文字起こし）が**並列に独立投入**される（`src/main.rs` の
  `submit_mixdown` / `submit_transcription`）。
- `src/mixdown.rs` に MP3 デコード（rodio `Decoder`）→ f32 PCM → i16 → `mp3lame-encoder`
  再エンコード → 0600 で原子的配置、の基盤が既にある（正規化はこの基盤に相乗りできる）。
- 録音ファイルは機微データ（0600/0700、`docs/rules/security.md`）。上書きは
  一時ファイル→rename の原子的配置で行う（whisper_model と同じ流儀）。

## 要件

- 録音停止後のバックグラウンド処理で、各音源（`mic.mp3` / `system.mp3`）のピークレベルを
  測定し、**極端に小さい音源だけ**を正規化して**上書き**する（正常な音源は無加工）。
- 正規化は後続処理より先に行い、**ミックス（`mix.mp3`）と文字起こしは正規化後の音声を
  使う**（後処理を「正規化 → ミックス → 文字起こし」の直列パイプラインへ再編）。
- 判定と正規化のパラメータ（初期値。実装時に実データで調整）:
  - 発動しきい値: ピーク < **-30 dBFS**（正常な発話はピーク -12〜-3dB 程度。今回の実例 -35dB
    を確実に拾い、少し小さめの正常録音は触らない）。
  - 目標: ピーク **-3 dBFS**（ピーク正規化。クリップせず単純増幅で歪まない）。
  - ゲイン上限: **+40 dB**（ノイズフロアの過剰増幅を防ぐ）。
  - 実質無音ガード: ピークが極端に低い（例 < -70 dBFS ≒ 本当に何も録れていない）ときは
    正規化しない（無音を爆音ノイズにしない）。
- 発動時はログで知らせる（例: `Normalizing mic.mp3 because it is too quiet (peak -35.1 dBFS,
  applying +32.1 dB)`。ファイル名のみ、フルパスは出さない）。診断性のため、非発動時も
  停止後に各音源のピークを 1 行ログする。
- スコープ外:
  - リアルタイム AGC（録音中のゲイン処理）。
  - OS の入力ボリュームの監視・復元（会議アプリと奪い合いになる）。
  - ラウドネス（LUFS）ベースの本格ノーマライズ・コンプレッション（ピーク正規化で十分）。
  - 正規化の設定 UI（固定パラメータで開始。要望が出たら後続）。

## 確定した論点

ユーザー確認で決定:

1. **主対策は停止後の自動正規化**（リアルタイム AGC・デバイスゲイン監視は不採用）。
2. **対象は極端に小さい音源のみ**（正常録音は無加工で元の音質・ダイナミクスを保つ）。
3. **正規化版で上書き**（`mic.orig.mp3` 等は残さない。ファイル構成を増やさない）。

調査・解析で確定:

4. 音声情報は存在する（whisper が認識済み）ため、増幅で実用レベルに戻せる。
5. `mixdown.rs` にデコード→再エンコード→原子的配置の基盤があり、正規化は同じ部品で書ける。
6. 現在は mix と文字起こしが並列投入のため、**正規化を効かせるには直列化が必要**
   （文字起こしを正規化・ミックス完了後に投入する連鎖へ変更）。

## 実装方針

- **後処理パイプラインの再編（`src/mixdown.rs` を後処理ワーカーへ拡張）**:
  `MixWorker` のジョブを「セッションの後処理」1 本にする:
  1. 各音源（存在する `mic.mp3` / `system.mp3`）のピークを測定し、しきい値未満なら
     正規化して上書き（一時ファイル→rename、0600）。
  2. 両音源があれば `mix.mp3` を生成（既存処理。正規化済み PCM を使うため二重デコードを
     避けられるなら流用する）。
  3. 完了後に `TranscribeWorker` へ投入（`MixWorker::start` に transcriber のハンドルを
     渡して連鎖させる）。`main.rs` の停止フックからは後処理ワーカーへの投入 1 回になり、
     `submit_transcription` の直接呼び出しは後処理ワーカー内へ移る（自動/手動の停止経路は
     従来どおり 1 箇所を通る）。
  - 文字起こしの設定 OFF のときは手順 3 をスキップ（現在の `submit_transcription` の
    ガードを移設）。
- **正規化の中核（純粋部分をテスト可能に）**:
  - `peak_of(pcm: &[f32]) -> f32`、`gain_for(peak, target, max_gain) -> Option<f32>`
    （しきい値・無音ガード込みで「かけるべきゲイン」を返す。かけないなら `None`）、
    `apply_gain(pcm, gain)`。dB 変換ヘルパ。単体テストで境界（しきい値・上限・無音）を固定。
  - デコード→ゲイン→i16→エンコードは mixdown の既存部品を共用（重複を作らない）。
- **メモリ**: 59 分 1ch f32 ≒ 680MB。デコード→処理→エンコードの間だけ保持し、move で
  段階へ渡して早期解放（`docs/rules/performance.md`）。mix 生成と連続する場合も同時に
  全音源を持ちすぎない順序にする。
- **#69（文字起こし状態表示）との関係**: 本件は文字起こしの投入タイミングを後処理完了後へ
  移すため、#69 の「Transcribing」開始時点も自然に「正規化・ミックス後」となる。同じ停止後
  経路を触るため、**本件を #69 より先に実装**する（または後発がリベース）。

## 実装ステップ

1. **正規化の純粋部分**: ピーク測定・ゲイン判定（しきい値/上限/無音ガード）・ゲイン適用と
   dB ヘルパを実装し、単体テストで境界を固定（-35dB 実例→発動、-20dB→非発動、無音→非発動、
   上限クリップ）。
2. **正規化の実行**: デコード→ゲイン→再エンコード→一時ファイル→rename（0600）を
   mixdown の部品で実装。手元の実データ（該当セッションのコピー）で正規化 →可聴になることを
   確認。
3. **パイプライン再編**: `MixWorker` を「正規化→ミックス→文字起こし投入」の直列ジョブへ
   拡張し、`main.rs` の停止フックを後処理投入 1 本に整理。自動/手動停止・文字起こし OFF/ON の
   各経路を確認。
4. **ログ**: 各音源のピークと正規化の発動/非発動を英語 1 行でログ（ファイル名のみ）。
5. **ドキュメント同期**: README（機能説明に自動正規化を追記）・docs/CONTEXT.md（設計判断:
   「会議アプリの AGC で極小音量になった録音は停止後に正規化する。デバイスゲインは触らない」）。
6. **仕上げ**: `cargo build` / `cargo fmt --check` / `cargo clippy --all-targets -- -D warnings` /
   `cargo test`。実機で Meet 録音を再現し、停止後に mic が可聴レベルへ正規化され、mix・
   文字起こしにも反映されることを確認。

## 影響範囲・リスク

- **影響を受けるファイル/モジュール**:
  - 変更: `src/mixdown.rs`（後処理パイプライン化＋正規化）、`src/main.rs`（停止フックの
    投入整理）。README・docs/CONTEXT.md。
  - 変更なし: `src/recorder.rs`（録音側は無変更）、`src/transcribe.rs`（投入元が変わるのみ）。
- **リスクと対策**:
  - **誤発動（正常だが静かな録音を増幅）**: しきい値 -30dBFS は正常発話（-12dB 前後）から
    十分離す。発動時は必ずログし、パラメータは const で調整しやすくする。
  - **ノイズ増幅**: ゲイン上限 +40dB と無音ガードで、ヒスノイズだけの爆音化を防ぐ。増幅で
    ノイズフロアも上がるのは原理的に不可避（それでも無音よりはるかに良い）。
  - **再エンコードによる音質劣化**: 128kbps MP3 の再エンコード 1 回分。発動時のみなので
    正常録音には影響しない。
  - **後処理時間の増加**: 正規化発動時はデコード＋エンコードが 1 回増える（59 分で数十秒
    オーダー）。バックグラウンドの逐次処理で UI は塞がない。
  - **文字起こし開始の遅延**: 直列化により、ミックス完了まで文字起こしが始まらない
    （従来は並列）。正しい音声で文字起こしするための意図的な変更として PR に明記。
  - **上書きの安全性**: 一時ファイル→rename の原子的配置。途中失敗時は元ファイルが残る。
- **原因（Meet の AGC）自体は直せない**: 本対策は対症療法。将来リアルタイム対策（録音中の
  レベル警告など）が欲しくなったら別プランで扱う。
