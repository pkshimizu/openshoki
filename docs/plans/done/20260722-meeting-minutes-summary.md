# 文字起こし結果から議事録要約を作成する

- 作成日: 2026-07-22
- ステータス: ステップ 1（モデル・品質の検証、#78。結果は末尾「ステップ 1 の検証結果」参照）・
  ステップ 2（モデル DL 基盤の一般化、#79）・ステップ 3〜4（要約コアとワーカー、自動連結と
  設定トグル、#80）が完了。**既定モデルは Qwen2.5-7B-Instruct Q4_K_M**（末尾「採用モデル」参照）。
  ステップ 5（Recordings ウィンドウでの表示と手動生成、#81）は未着手

## 概要

録音セッションの文字起こし（`mic.json` / `system.json`）から、議事録に必要な事項
（議事概要・議題内容・決定事項・アクションアイテム）をまとめた要約を生成する。
生成は**オンデバイス LLM**（llama.cpp）で行い、「音声・文字起こしを外部送信しない」という
プロジェクトの根幹方針を要約でも維持する。文字起こし完了後の自動生成（オプトイン）と、
Recordings ウィンドウからの手動（再）生成の両方を提供する。

## 背景・前提（コンテキスト）

- 文字起こしはオンデバイス whisper（`whisper-rs`）で録音停止後にバックグラウンド実行
  （オプトイン・既定 OFF）。`TranscribeWorker` は mpsc ＋逐次スレッドの構成で、
  `submit(TranscribeJob)` と `status_of(session_dir)` を持つ（`src/transcribe.rs`）。
  要約ワーカーはこれと同型に作れる。
- whisper モデルは初回に HTTPS で自動ダウンロード（SHA-256 検証・原子的配置・
  タイムアウト・サイズ上限。`src/whisper_model.rs`、`docs/rules/security.md` の定型）。
  LLM モデルの取得も同じ定型を使える（共通化の余地あり）。
- マージ済みトランスクリプトは `src/transcript.rs::load_transcript` が話者
  （Mic / System）ラベル付き・時刻順で返す。要約の入力にそのまま使える
  （Mic=自分の発話、System=相手側の音声、という区別を要約プロンプトに活かせる）。
- 認識言語は設定 `transcribe_language`（既定 `en`、主要 8 言語＋`auto`）。要約言語は
  これに追従させる（ユーザー確認済み）。
- Recordings ウィンドウの右ペイン（詳細）には #69（文字起こし状態表示・再実行ボタン）と
  #66（セッション削除ボタン）が手を入れる予定。ワーカー状態の UI 反映は
  「`Arc<Mutex<...>>` を表示中の 100ms tick で読む」流儀が確立している（#69 のプラン参照）。
- 大きなリソース（ML モデル）は**ジョブ単位でロードし、対象が無ければロードしない**
  （`docs/rules/performance.md`）。GB 級バッファは move で渡す。
- 機微ファイルは 0600 で作成する（`docs/rules/security.md`）。

## 要件

- 文字起こし済みセッションから、次の構成の議事録 Markdown を生成する:
  - **議事概要**（会議全体のサマリー数行）
  - **議題内容**（トピックごとの議論の要点）
  - **決定事項**（決まったこと）
  - **アクションアイテム**（誰が・何を・いつまでに。発話から読み取れる範囲で）
- 生成はオンデバイス LLM（llama.cpp）。**外部送信はしない**（通信はモデルの初回
  ダウンロード受信のみ、whisper と同じ建て付け）。
- 要約の言語は文字起こし言語（`transcribe_language`）に追従する（`auto` のときは
  文字起こし結果の言語に合わせるようプロンプトで指示する）。
- セッションディレクトリに `summary.md`（0600）として保存し、Recordings ウィンドウの
  右ペインで Transcript と切り替えて表示する。
- 生成タイミング: 設定 ON（既定 OFF のオプトイン）なら文字起こし完了後に自動生成。
  Recordings ウィンドウから手動（再）生成もできる。
- 未生成・生成中・失敗のセッションは落とさず縮退表示する（「Not Summarized Yet」等。
  文字起こしが無いセッションでは生成できない旨を示す）。
- 長い会議（数時間）でも完走する（コンテキスト超過はチャンク分割で処理）。
- スコープ外:
  - 外部 API（OpenAI 等）による要約（採用しない。将来必要になれば別プランで再検討）。
  - 要約の編集 UI・エクスポート（クリップボード/共有）・テンプレートのカスタマイズ。
  - 話者の個人名推定（Mic / System の区別のみ使う）。

## 確定した論点

ユーザー確認で決めた事項:

- **エンジンはオンデバイス LLM**（プライバシー方針の維持を最優先）。
- **文字起こし完了後の自動生成（オプトイン）＋手動（再）生成**の両対応。
- **`summary.md` 保存＋ Recordings ウィンドウ表示**。
- **要約言語は文字起こし言語に追従**（追加の設定項目を作らない）。

調査で解消した事項:

- **バインディングは `llama-cpp-2` クレート**（llama.cpp の Rust バインディング。
  whisper-rs と同じく CMake ビルドで、ビルド前提は既存と同じ）。
- **ワーカーは `TranscribeWorker` と同型の逐次ワーカー**を新設し、文字起こし完了時に
  設定 ON なら要約ジョブを連結投入する（`TranscribeWorker` に完了フック（要約ジョブの
  `Sender`）を渡す）。
  **訂正（#80 のレビューで判明）**: ワーカーの連結は投入順を決めるだけで排他にはならず、
  別セッションのジョブがキューにあれば whisper と LLM が並走する。CPU・メモリのピークを
  重ねないための直列化は、共有ロック（`src/inference_slot.rs`）で別途行った。
- **モデル候補は Qwen2.5-3B-Instruct の GGUF（Q4_K_M、約 2GB、Apache-2.0）を第一候補**
  とする（多言語（日英含む）・再配布可能ライセンス・サイズのバランス。最終確定は
  ステップ 1 の品質検証で行う）。
- **長文はチャンク分割の 2 段要約（map-reduce）**: セグメント列を時系列のまま
  トークン概算でチャンクし、チャンクごとの中間要約→最終の議事録生成の 2 段にする。
  チャンク分割・プロンプト組み立ては純粋関数にしてテスト可能にする。

## 実装方針

- `src/summarize.rs` を新設: マージ済みトランスクリプト→プロンプト組み立て→llama.cpp
  実行→`summary.md`（0600）書き出し、を行う `SummarizeWorker`（mpsc＋逐次スレッド、
  `submit` / `status_of` を持つ `TranscribeWorker` と同型）。
- プロンプトはセクション見出し（議事概要/議題内容/決定事項/アクションアイテムの各言語版）を
  固定で指定し、出力の Markdown 構造を安定させる。話者ラベル（Mic=the user,
  System=other participants）を入力に含める。
- モデル管理は `whisper_model.rs` の定型（SHA-256・原子的配置・タイムアウト・サイズ上限・
  ジョブ単位ロード）を共有ヘルパへ一般化し、whisper / LLM の両モデル定義から使う。
- 設定に `auto_summarize`（既定 OFF）を追加。ON かつ文字起こし成功時に自動で要約ジョブを
  投入する（文字起こし OFF なら要約も動かない）。
- UI（`ui/recordings-window.slint`）: 右ペインに Transcript / Summary の切替を追加し、
  `summary.md` を読んで表示（欠落・生成中・失敗は縮退表示）。手動の「Summarize」ボタンを
  詳細ペインに置く。状態の受け渡しは #69 と同じ `Arc<Mutex<...>>`＋tick 方式。
- #66 / #69 と同じ詳細ペインを触るため、**着手順を直列にする**（#69 → 本件の順が自然。
  ボタン配置・状態表示のパターンを踏襲できる）。

## ステップ 1 の検証結果（#78）

- 実施日: 2026-07-26
- 環境: macOS 26.5.2 / Apple M1 Max。`llama-cpp-2` 0.1.152
- **バックエンドは CPU（＋Accelerate BLAS）**。下記「Metal が効かない」参照。全数値が CPU 実行。
- 計測はページキャッシュがウォームな状態。同一条件 3 回で prefill 7.06〜7.09s と再現性は高いが、
  裏で cargo ビルドが走っていると prefill が 25% ほど落ちる（測るときは他を止める）。
- 道具: `examples/summary_probe.rs`。サンプルは `assets/samples/meeting-{ja,en}.txt`
  （実会議データを使わずに再現できるようにした架空のトランスクリプト）

```sh
cargo run --release --example summary_probe -- --model <path.gguf> --lang ja
cargo run --release --example summary_probe -- --model <path.gguf> --lang en --ctx 8192
```

長文の計測には `meeting-ja.txt` を N 回連結したものを使った（`for i in $(seq 1 6); do cat
assets/samples/meeting-ja.txt; done > long.txt`）。**同じ内容の反復**なので、prefill の時間
計測には使えるが（dense attention の計算量は内容に依存しない）、生成量や要約品質は
その長さの会議を代表しない。

### 1. `whisper-rs` と同居できるか → **CPU 構成では、できる**

どちらも ggml を同梱するためシンボル衝突が懸念だったが、`whisper-rs` 0.16 と
`llama-cpp-2` 0.1.152 は**同じバイナリにリンクでき、両方のネイティブコードが動く**。

確認できた範囲を正確に書くと: プローブは存在しないパスで `WhisperContext` を開いて失敗させて
いるだけなので、**whisper 側の ggml 計算パスは通っていない**。また下記のとおり両クレートとも
GPU バックエンドが未登録なので、**ggml-metal を両方が持ち込んだときの衝突は未検証**。
#80 で Metal を使うなら、その構成での同居確認を最初のゲートに置くこと。

### 2. Metal が効かない（このクレートのこのバージョンでは）

macOS aarch64 では `llama-cpp-sys-2/metal` がターゲット依存で有効になり `libggml-metal.a` も
ビルドされる。しかし**最終バイナリに Metal が入らない**:

- `libggml-metal.a` は `ggml_backend_metal_reg` を定義している（`nm` で `T`）。
- `libggml-base.a` はそれを**参照していない**（`U` が 0 件）。参照が無いのでリンカがアーカイブ
  ごと落とす。
- 結果、実行時のデバイス一覧は `BLAS (Accelerate)` と `CPU` だけで、`with_n_gpu_layers` は
  **黙って無視される**（エラーにならない）。

`features = ["metal"]` を足しても再ビルドすら起きない（ターゲット依存で既に有効なため）。
**feature 指定では直せない。** #80 で GPU を使うなら、クレートの更新か別バインディングの
検討が要る。プローブは起動時にデバイス一覧を出すので、取り違えたらすぐ分かる。

### 3. 品質

**判定基準**（`summary_probe` の出力を grep して機械的に判定。**「正しいものが在るか」だけでなく
「誤ったものが無いか」も見る**。前者だけだと、正しい日付が別の場所に在るのに action item では
捏造されている、という取りこぼしが起きる）:

| 項目 | 日本語 | 英語 |
|---|---|---|
| ロールバック基準 | `1%` を含む | `one percent` を含む |
| モニタリング担当 | `モニタリング` を含む | `monitoring` を含む |
| ポストモーテム | `ポストモーテム` を含む | `postmortem` を含む |
| 担当者の帰属 | `田中` を含む | `Tanaka` を含む |
| 誤った日付 | 木曜以外の曜日を**含まない** | Thursday 以外の曜日を**含まない** |
| 雛形・プロンプト語の漏れ | `（なし）` `（未定）` `<担当` を**含まない** | Action Items にバッククォートや `<owner>` を**含まない** |

**結果（確定プロンプト、`--ctx 8192`）**:

| | 3B 日本語 | 7B 日本語 | 3B 英語 | 7B 英語 |
|---|---|---|---|---|
| ロールバック基準 | ○ | ○ | ○ | ○ |
| モニタリング担当 | ○ | ○ | **×** | ○ |
| ポストモーテム | ○ | **×** | ○ | ○ |
| 担当者の帰属 | ○ | ○ | ○ | ○ |
| 誤った日付 | **あり** | なし | なし | なし |
| 雛形・プロンプト語の漏れ | **あり** | なし | **あり** | なし |
| 見出し 4 つの構造 | ○ | ○ | ○ | ○ |
| 言語の取り違え | なし | なし | なし | なし |

**失敗の質が違う**。3B は**誤った出力**を出す:

- 日本語: `- Mic: 日曜の 15 時にモニタリングを担当（なし）` — 本文では正しく「木曜の 15 時」と
  書いているのに、アクションアイテムで**曜日を捏造**した。さらに期限欄にプロンプト由来の
  `（なし）`（本来は「該当が無い見出し」用の語）が漏れている。
- 英語: ``- Tanaka: Pick up config diff check in the next sprint (`Next sprint`)`` — 期限欄に
  バッククォートごとテンプレートの痕跡が残る。

7B の失敗は**取りこぼし**だけ（日本語でポストモーテムのアクションアイテムを落とす。決定事項には
書いている）。議事録という用途では、捏造した日付は読んだ人が誤って行動しうるぶん、取りこぼしより
質が悪い。

ただしこれは**4 分・手書きサンプル 1 本**の結果で、統計的な差ではない。

#### プロンプトの反復で分かったこと（重要）

初版は「3B 日本語だけ幻覚が出て、決定事項も落とす」という結果だったが、**それはプロンプトの
欠陥によるものだった**。3 回作り直して分かったこと:

1. **見出しの役割を書かないと `## 議題内容` が空になる**（内容が概要へ流れ込む）。見出しごとに
   1〜2 行で役割を書くと解消した。
2. **few-shot の例に評価サンプルと同じ語彙（`田中さん` / `CI に設定差分`）を使うと、品質評価が
   汚染される**。「抽出できた」のか「例を写した」のか区別できない。
3. **例の語彙をサンプルと重ならない人名（`山田` / `Yamada`）に変えると、今度はその人名が
   架空の担当者として出力に漏れた**（3B 英語は例を丸写し、7B 日本語は実在のタスクの担当に
   例の人名を当てた）。**人名入りの例は置いてはいけない。**
4. **例を完全に外すと書式が崩れる**（`- 担当: Mic (木曜日の 15 時まで)` のように「やること」が
   消える、テンプレートをバッククォートごと写す）。
5. 落としどころは**山かっこのプレースホルダ**（`- <担当者名>: <やること>（<期限>）`）＋
   「担当者名は文字起こしに出てきた人だけ」という制約。これで書式も崩れず、架空の担当も出ない。

確定プロンプトの実物は、**出荷実装の `src/summarize.rs` の `MINUTES_SYSTEM_JA` /
`MINUTES_SYSTEM_EN` が正**（日本語版は検証時と完全一致。英語版は #80 で出力言語と見出しの
扱いをパラメータ化したので文面が変わっている）。`examples/summary_probe.rs` の
`SYSTEM_JA` / `SYSTEM_EN` は #78 当時の検証用スナップショット。

### 4. 速度とピークメモリ

**ピーク RSS は会議の長さではなく `n_ctx` で決まる**（KV キャッシュを起動時に一括確保するため）。
下表はすべて `--ctx 8192`。参考: `--ctx 32768` にすると 3B で +0.84 GB、7B で +1.31 GB になる。

| モデル | 会議長 | プロンプト | prefill | 生成 | 合計 | ピーク RSS（ctx 8192） |
|---|---|---|---|---|---|---|
| 3B Q4_K_M | 4 分 | 1,168 tok | 10.3s（114 tok/s） | 14.8s（35 tok/s） | 25.1s | 3.72 GB |
| 7B Q4_K_M | 4 分 | 1,168 tok | 21.8s（54 tok/s） | 31.7s（16 tok/s） | 53.5s | 8.18 GB |

「合計」は prefill ＋ 生成で、**モデルのロードは含まない**（プローブが出す `total` は load 込みで、
3B 26.9s / 7B 56.9s）。load は mmap なので初回のページインを含まず、コールドではさらに遅い。

長文（`--ctx 32768`、3B、同一内容の反復サンプル）:

| プロンプト | prefill | tok/s |
|---|---|---|
| 1,168 tok | 10.3s | 114 |
| 5,008 tok | 71.8s | 70 |
| 9,575 tok | 200.1s | 48 |

（1,168 / 5,008 は確定プロンプトでの実測。9,575 は旧プロンプト時の値で、比率の傾向を見る目的で
残している。超線形性は確定プロンプトでも同じ: 4.29 倍のトークンに対し 6.97 倍の時間。）

**ピーク RSS には GGUF の file-backed mmap ページ（3B で約 2.0 GB）が含まれる**。同時に見た
`footprint` の `phys_footprint` は 1.8 GB 程度で、macOS が逼迫時に見るのは後者。「3B の実行に
3.7 GB の空きが要る」と文字どおりには読めない（ただし逼迫すると重みが再読み込みになり性能は崩れる）。

`load` の欄は mmap のため実際のページインを含まない（初回のページインは prefill 側に乗る）。
コールド実行では 7B の `load` が 5.0s、短いプロンプトの prefill が 28 tok/s まで落ちた。
**上表はすべてウォーム状態の値**で、ユーザーが体感する初回はこれより遅い。

### 5. チャンク分割 → **要る。閾値は約 4,000 トークン**

コンテキスト長は理由にならない（Qwen2.5 の学習時コンテキストは 32,768）。**理由は prefill が
超線形に伸びること**: 3B でトークン数 4.4 倍に対し時間 7.3 倍、8.5 倍に対し 20 倍。

- トークン/文字の実測比: **日本語 0.627 tok/文字**、**英語 0.294 tok/文字**。定型部分
  （システムプロンプト＋チャットテンプレート）は空のトランスクリプトで実測して
  **日本語 400 / 英語 277 トークン**（確定プロンプトでの値）。
- 文字数は `[mm:ss] Speaker: ` のプレフィックス込みの全文字数で数えている（トークン比も同じ
  数え方なので換算は自己整合する）。この数え方での**サンプルの密度は日本語 304 文字/分・
  英語 506 文字/分**。実発話だけなら日本語 876 文字 / 英語 1,688 文字で、プレフィックスが
  全体の 3 割（日本語）を占める。**プレフィックスの有無で分換算は変わる**ので、#80 で分単位の
  見積もりを出すならこの定義を添えること。
- 4,000 トークン ≈ 本文で**日本語 5,800 文字（約 19 分）／英語 12,800 文字（約 25 分）**。
- **既定モデルが 7B なら、この閾値でもチャンク 1 つに約 110 秒かかる**（4,967 tok で 36 tok/s）。
  2 時間の会議なら 6〜7 チャンク＋reduce で 15 分超になる。モデルごとに閾値を変えるか、
  長時間会議での所要時間をユーザーに提示する必要がある。
- **map-reduce の 2 段目（中間要約の再 prefill ＋ 生成）は未計測**。「全体の時間がトークン数に
  ほぼ比例する」は推定であって検証していない。

### 6. 実装上の注意（本実装で必ず要る）

- **プロンプトは `n_batch`（既定 2048）以下に分けて `decode` へ渡す**。一括で渡すと
  llama.cpp が**アサートで abort し、プロセスごと落ちる**（検証中に実際に落ちた）。
  常駐アプリでこれをやると録音中でも巻き添えになる。プローブは 512（`n_ubatch` に合わせた値）
  ずつ投入している。
- **プロンプト＋生成が `n_ctx` を超えたら、走らせる前に落とす**。超えたまま進むと最初の
  `decode` が `NoKvCacheSlot` で失敗し、原因が分かりにくい。
- **生成結果はトークンごとに文字列化せず、バイトで受けてから UTF-8 にする**。日本語は
  マルチバイト文字がトークン境界をまたぐため、トークン単位で `String` にすると欠落する
  （検証中に「議事概要」が「事概要」になった）。
- サンプリングは貪欲でよい。ただし**決定性はバックエンドとスレッド数を固定した場合のみ**
  成立する（Metal を有効化したら品質表は測り直し）。

### 7. この検証で確かめていないこと

- **実際の文字起こし出力での品質**。サンプルは手書きで、句読点が完璧・認識誤りゼロ・
  フィラーも言い直しも無い。実運用の入力より明確に易しい。
- **本題から外れた雑談を落とせるか**。サンプルに雑談が入っていない。
- **map-reduce の 2 段目**（未実装・未計測）。
- **Metal 構成での速度・メモリ・同居**（上記のとおりリンクされない）。

### 採用モデル（**2026-07-26 確定**）

**カタログに 2 つ載せ、既定は Qwen2.5-7B-Instruct Q4_K_M**（ユーザー判断）。

判断が 2 転したので経緯を残す。(1) 初版のプロンプトでは「3B 日本語だけ幻覚が出る」と見えて
7B を既定にした → プロンプトの汚染が原因だった。(2) 直したら差が消えたように見えて 3B へ変更
