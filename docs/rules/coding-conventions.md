# 実装ルール: コーディング規約

## Rust edition は 2024

このプロジェクトは **Rust edition 2024** を使う（`Cargo.toml` で指定済み）。edition 2024 は
Rust 1.85 以降で安定しており、`if ... && let ...` の let-chains などが使える。

- 「edition 2024 は存在しない／未サポート」という指摘は誤り。`cargo build` が通ることで確認できる。
- `cargo clippy` が `collapsible_if` 等で let-chain への結合を提案したら、それに従ってよい。

## マジックナンバーは const にする

意味のある数値はリテラル直書きにせず、名前付き定数にして意図を表す。

```rust
// NG
let bright = [0xD0, 0x21, 0x1c];

// OK（`src/tray.rs` の録音中グリフ）
const RECORDING_BRIGHT: [u8; 3] = [0xD0, 0x21, 0x1c]; // 明滅の明るい側の赤
```

## 状態に対応する UI 文言は const にして散らさない

ウィンドウの可視状態とトレイ項目のラベルのように、**状態と表示文言が対応する**ものは、
文字列リテラルを複数箇所に直書きしない。1 箇所変えて他方が追従漏れすると、表示状態と
ラベルが食い違う「ありえない状態」になる。

- ラベルは `pub const TOGGLE_LABEL_SHOW: &str = "...";` のように定数化し、初期値・更新の
  双方から同じ定数を参照する。
- 表示/非表示のような対の操作は、状態変更とラベル更新をまとめた小関数
  （例: `show_window` / `hide_window`）に切り出し、対応関係を一箇所で保証する。

## 検証コマンド

コミット前に次が通ること（PR の確認事項と対応）:

- `cargo build`
- `cargo fmt --check`
- `cargo clippy --all-targets -- -D warnings`

## 手順書に書くコマンドは、その手順の目的を満たす一式にする

「上げ方」「動かし方」のような手順を書くとき、**検証コマンドを部分集合で書かない**。
`rust-toolchain.toml` の上げ方に `cargo clippy` だけを書いて `cargo fmt --check` を落として
いたが、CI は fmt から順に回るので、手順どおりにやっても CI で落ちる——「手元で通れば CI で
通る」ことを目的にした手順が、その目的を満たしていなかった。個別に並べ直さず、
上の「検証コマンド」を参照する形にする。

引用元が「ここでは効かない」と書いている対策を、手順へ写さないこと。同じファイルで
`docs/rules/testing.md` の `touch` 手順を引いていたが、そこには「バージョン差による見逃しは
別問題」と明記してあった。**引用するときは引用元の但し書きまで読む**。

## 実装を変えたら PR 本文も直す

PR 本文は差分にも CI にも出ないので、途中で方針を変えると古い説明が残る。#157 では
「アクションにファイルを読ませる」と書いたまま、実装は「アクションを使わない」に変えていた。
後から PR を開いた人は、**採用しなかった案を採用したものとして読む**。方針が変わった
コミットを積んだら、その場で `gh pr edit --body-file` で本文も直す。

## 状態は「status + Option の袋」にしない

`status` と `Option` を並べた構造体は、**ありえない組み合わせを型が許す**（`Done` なのに理由が
ある、`Failed` なのに進捗がある）。そうなると正しさは実行時のガードとテスト頼みになり、
書き込む場所が増えるたびにガードを足し忘れる余地ができる。

状態ごとに変種を作り、**その状態でだけ意味のあるものを持たせる**（`TranscribeState` /
`SummarizeEntry`）。副作用として:

- 「進行中のときだけ進捗を書く」が実行時の `if` ではなく**パターンで保証される**
- 遷移で消し忘れが起きない（変種ごと差し替えるので、古いフィールドが残らない）
- 実際には到達しない `Option::None` のためのフォールバック文言とテストが消える

**逆向きも見る**: 全バリアントが持つものは変種の外へ出さず、**使う変種だけに持たせる**
（#159 では、待っている間・終わったあとのモデル名は誰も読んでいなかった）。

## 一覧を「絞り込んだ側」と「全部」で二重に持ったら、増減の経路を全部そろえる

表示用に絞り込んだ一覧と、元の全件を別々に持つと、**片方だけ更新する経路**が必ず残る。#161 では
削除が絞り込み後の一覧からしか消さず、検索を解除するとゴミ箱へ移した録音が戻ってきた。

- 増減する経路（追加・削除・走査し直し）を数え上げ、**全部が両方を触る**ことを確かめる
- 添字は絞り込みで食い違うので、もう片方は**ディレクトリなどの同一性で引く**
- 派生する表示（件数など）も 1 つの関数へ寄せる（`main::apply_list_counts`）

## 「こちらが設定した値」を、書かれた値として読まない

外部ライブラリに渡した設定は、**黙って別の値に落とされる**ことがある。#162 では
`set_brate(Kbps128)` が成功するのに、入力のサンプルレートが低いと LAME が MPEG-2.5 の 64kbps へ
落とし、ファイルサイズからの長さが 2 倍ずれた（8kHz を報告する Bluetooth ヘッドセットで起きる）。
録音自体は正常に残るので、どこにも失敗が出ない。

出力から**実際の値を読む**（MP3 なら先頭フレームヘッダ 4 バイト）。設定値を前提にするなら、
その前提が成り立つことをコード側で保証する（範囲外を弾く・変換する）。

## 「在る」と「完成している」を区別する

書きかけのファイルが「在る」状態になると、それを見る側は**もっともらしく間違った答え**を出す。
#162 では `mix.mp3` を直接 truncate + write していたため、生成中に一覧を開くと 1 時間の録音に
`00:03` と出た（サイズから長さを見積もるため）。

一時ファイルへ書いてから置き換える（`atomic_replace::PartFile`）。**在る＝完成している**を
不変条件にすれば、読む側は状態を気にしなくてよい。

## 同型の引数を並べた関数に切り出さない

「同じ選び方を共有する」ために関数へ切り出しても、**引数が同じ型ばかりなら順序を取り違えても
通る**。#162 では `playback_source(&dir, has_mic, has_system, has_mix)` にしかけたが、これでは
共有した意味が「呼び出し側が順序を間違えないこと」に化けている。

共有すべきが**組み上がった値**なら、先に組んでからメソッドを呼ぶ。そうすれば選び方が 1 つで
あることが構造で決まる。

## 背景処理の結果は、届いた時点の事実で組み直す

背景スレッドが返すのは**投げた時点のスナップショット**なので、届くまでに変わったものは載って
いない。#161 では検索結果の「文字起こしがあるか」が古く、直後に組む行（現在の状態を見る）と
食い違った。**行の差分更新は「変化なし」と判断してしまう**ので、その食い違いは以後どの tick でも
直らない。

- 結果に載っている情報のうち、**別の場所が正を持つもの**は届いた時点で引き直す
- 引き直す元は、**同じ瞬間の同じ情報源**にする（1 周遅れで更新される別のコピーから写さない）
- 消えているかもしれないものは落とす（`retain` で存在を確かめる）

## 世代で捨てるだけでなく、走っているものを降ろす

「古い結果を世代で捨てる」だけだと、**走っている処理は最後まで走り切る**。選択のように数回なら
それでよいが、打鍵のたびに投げるもの（検索）では、1 語打つ間に何本もが全件を読み切り、いま欲しい
結果を自分で遅くする。

`Arc<AtomicU64>` を渡して**重い単位ごとに世代を確かめて降りる**（`main::SEARCH_WATCHERS` /
`LOAD_WATCHERS`）。捨てる経路（開く・閉じる・解除）は全部その関数を通す。

## 既存の doc コメントの直下に宣言を差し込まない

`/// …` の直後に新しい `const` や `component` を足すと、**その doc は新しい宣言のものになり**、
元の型・関数は doc を失う。差分では「1 行足しただけ」に見えるので、レビューでも見落としやすい。
#154 では `JobOutcome` の doc が `PANIC_REASON` に付き、Slint のウィンドウ全体のレイアウト説明が
新しい部品の説明として読める形になった。

足すときは、その宣言自身の doc を書いてから**既存の doc の上か下か**を確かめる。

## 機能を変えたらドキュメント・コメントも同じ PR で同期する

機能を追加・変更・削除したら、実装だけでなく次も**同じ変更内で**更新して陳腐化させない
（レビューで「削除した機能の説明が残っている」「出力ベースの記述のまま」等が繰り返し出やすい）:

- `docs/CONTEXT.md`（ドメイン・機能の説明）の該当箇所。
- `README.md` の「現状／今後」など該当箇所（実装済みを「今後」に残さない）。
- 変更箇所の周辺コメント・doc コメント（削除した経路・旧方式を指す表現を残さない）。開始側と
  停止側など、対になる関数のコメントの用語も揃える。
- 「後続 #NN で対応」のような**前方参照コメント**（README・doc コメント）は、その issue を
  実装する PR で必ず消す/書き換える。差分に当該ファイルが含まれず見落としやすい（grep で
  `#NN` を探す）。
- **他の issue へ書いたコメント**（「この資産はこう使う」等の申し送り）も対象。差分にも CI にも
  出ないので、方針を変えたら `gh issue view <NN>` で読み直し、訂正コメントを足すか編集する。
  訂正は**古いコメント全部**を対象にする（1 通だけ直すと残りが旧方針のまま残る）。

## コメントに書いた「保証」は実装で作る（作らないなら書かない）

「同時に走ることはない」「必ず先に解放される」のような**資源・順序の保証**をコメントに書くと、
後から読む人はそれに寄りかかって設計判断をする。実装がその保証を作っていないと、静かに壊れる。

- ワーカーが別スレッド・別キューなら、**ジョブを投げた順序は実行の排他を保証しない**。
  直列化したいなら共有のロック等で実際に排他する（`src/inference_slot.rs`。whisper と
  要約 LLM のピークを重ねないための実例）。
- 実装しないと決めたなら、コメントは**保証されている範囲だけ**に書き直す
  （「同一セッションでは重ならない。別セッションとは並走しうる」のように）。
- 同じ主張を Rust の 2 箇所と `docs/CONTEXT.md` に複製すると、直すときに片方が残る
  （下の「正は 1 箇所」も参照）。

## 破壊的操作の判定キーに、表示・ログ用の文字列を使わない

「このファイルを消してよいか」のような**破壊的操作の可否**を、表示やログのために置いた文字列
（`ModelSpec::kind` の `"Whisper speech"` 等）の一致で決めない。文言は UI 調整で変わるもので、
変えた瞬間に判定が静かに崩れる（しかも多くの実装は `_ => false` へ落ちるので、**消せる側**に
転ぶ）。

- 識別は**型か、実体を引く関数**で行う（`whisper_model::spec_for(id)` のようなカタログ引き、
  または `enum`）。文言はあくまで表示に使う。
- 「文言の一致」を残すなら、その文言が判定キーであることを doc に書き、突き合わせのテストを置く
  （テスト用の偽データが実在しない文言を使っていると、写像が壊れても緑のまま通る）。
- 表示用の定数を判定にも使い始めたら、その定数の doc を**両方の役目**に更新する（#117 の
  `KIND` が実例）。

## 共有状態の「見てから決める」は 1 回のロックに畳む

`status_of()` で見てから `cancel()` する、のように**判定と行動を別々のロック取得に分ける**と、
その隙間で別スレッドが状態を進める。ワーカーが絡む経路では必ず開く窓なので、「起きにくい」で
済ませない（#133 では、キュー待ちだと判定した直後にジョブが走り出し、生成中のセッションを
削除できてしまう窓が開いていた）。

- 判定と行動を 1 つのメソッドにまとめ、**1 回のロックの中で**両方やる。呼び出し側は結果
  （enum）だけで分岐する（`SummarizeWorker::cancel_queued` → `CancelOutcome`）。
- 戻り値を捨てると窓が閉じないので、この種の API には `#[must_use]` を付ける。
- 「いま有効なのはどれか」の判断材料は**1 つの共有状態に集約する**。別のマップや集合に
  分けて持つと、2 つのロックの順序と整合が新しい競合になる（#133 は「取り消し済みジョブの
  集合」を廃し、状態マップのジョブ通番だけで判断する形にして、同じセッションが複数キューに
  載るケースごと解消した）。
- 採番のような「ロックの中でしか触ってはいけない値」は、その状態と**同じミューテックスに
  入れて型で縛る**（別の `AtomicU64` にすると、制約がコメントでしか守られない）。

## 同じ背景説明を複数箇所に重複させない（正は 1 箇所、他は参照）

ある実装の「なぜ」（OS 固有の都合・回避策の背景など）を、呼び出し側インラインコメント・
関数の doc コメント・`docs/CONTEXT.md` の複数箇所にフルで書き写さない。片方を直すと他方が
食い違う二重管理になり、読む負荷も増える。

- 詳細な背景は **1 箇所（原則は関数の doc コメント）** に集約し、他はそこを指す短い参照に
  留める（例: 「理由は `hide_dock_icon` の doc コメント参照」）。
- `docs/CONTEXT.md` は「今後も効く設計判断」を要約する場で、コード内 doc コメントは実装
  詳細を書く場。両方に同じ長文を貼らず、粒度を分ける。
- 対象ファイルの**列挙**（「これとこれをコミットする」等）も同じ。どうしても複数箇所に書くなら
  **例外基準**で書く（「A を除いてすべて」）。列挙のまま書くと、対象が増えたときに片方だけ
  古くなる。方針を変えたら grep で全箇所を洗う（レビューで毎ラウンド別の書き漏らしが出た）。

## `RefCell` の借用を持ったまま、作り直しの経路を呼ばない

判定のために `borrow()` した `Ref` を持ったまま「表示を作り直す」関数を呼ぶと、その先で同じ
セルが `borrow_mut()` され、**`BorrowMutError` で常駐プロセスごと落ちる**。`Ref` は `Drop` を
持つのでスコープの末尾まで生きており、NLL でも早く解放されない。

判定はブロックに閉じて値だけ取り出し、借用を返してから作り直しを呼ぶ:

```rust
let busy = {
    let override_files = list.override_files.borrow();
    row_facts(&source, &models_context(…, &override_files)).busy
};
refresh(&models, …); // ここで borrow_mut される
```

コンパイラは通すので、**借用の寿命は読んで確かめるしかない**。共有ハンドルを持つ型の doc に
「作り直しの前に借用を残さない」と書いておく（`windows::models::ModelListHandles` が実例）。

## 「取り違えられない」と書くなら、型かテストのどちらかで作る

同じ型のものが 2 つ並ぶとき（2 つの一覧、2 つのウィンドウ）、マクロや関数でまとめても
**組を間違える余地は消えない**——`ModelListHandles` はどちらの一覧も同じ型なので、渡し違えても
コンパイルは通る。まとめて減らせるのは「間違えられる箇所の数」であって、間違えられること自体では
ない。

だから doc には作った保証だけを書く:

- 型で防げるなら「型で防いでいる」と書く。
- 防げないなら「**決まる場所を 1 か所にした**」と書き、その 1 か所を検査するテストの名前を添える
  （`windows::models::each_window_owns_its_own_list` が実例）。

守れない約束を書くと、次に触る人がそれを信じて確認を省く。#141 のレビューで実際に指摘された。

## 「いま走っているもの」と「いま最新のもの」を別々の値で持たない

同じ対象について「走っている印」と「状態マップの最新エントリ」の 2 つを持つと、両者がずれた
瞬間に、片方だけを見た判断が静かに間違う。

#163 の時点で、`RunningJob` が通番を持たず `stop` が「セッションが一致するか」だけで走行中を
判定していた。同一セッションに「走っている古いジョブ」と「積み直された新しいジョブ」が同時に
在ると、中断フラグは**古いほう**に立ち、`Stopping` の表示は**新しいほう**のエントリに書かれ、
その後ワーカーは通番が一致するので新しいほうを走らせた——**Stop を押したのに最後まで走る**。

印の側にも通番を持たせ、止めるときは通番ごとマップへ書き戻す。こうすると「止めた対象」が 1 つ
に決まり、後続は通番の照合で自動的に捨てられる。あわせて、デキュー時の照合は**通番と状態の
両方**を見る（状態を足したときに、通番だけの照合が静かに通ってしまうのを防ぐ）。

## 中断フラグは、重い処理の**手前で毎回**見る

止める口を作るとき、いちばん長く待たされる区間の手前に確認が無いと、機能として成立しない。

#163 の最初の実装は、中断フラグを見るのが音源ループの先頭だった。その手前にはモデルの取得
（分オーダー）・推論スロットの待ち（別のモデルが握っていれば分オーダー）・モデルのロード
（秒〜十数秒）が並んでいて、**止めたい動機がいちばん強い場面**（間違ったモデルで流し始めた＝
まさにダウンロード中）でまったく効かなかった。

`AtomicBool::load` は 1 行で済む。重い呼び出しの前後に素直に並べる。

## 「残す」を足すときは、既に在るものより悪くなっていないか見る

縮退を「捨てる」から「読めるところまで残す」へ変えると、書き出す経路が新しく増える。その宛先に
**前の実行の成果物が在る**なら、上書きは改善どころか損失になりうる。

#164 では、音源を最後まで読めなくなったときに途中結果を保存するようにしたが、既存の
`<音源名>.json` を無条件で上書きしていた。前回は最後まで読めていた（＝完成品）ケースがあり、
しかも音源がもう最後まで読めない以上、失われた完成品は二度と作れない。「途中でも残す」ための
変更が、**完成品を途中結果で置き換える**という逆向きの損失を生んでいた。

- 保存するかどうかの条件を 1 箇所へ集め（`transcribe::write_decision`。#164 当時は `partial_is_worth_keeping`）、
  呼び出し側が理由を数え上げなくて済むようにする
- 「残った」と UI に言うなら、**開いて読む行がある**ことまで確かめる。書いたが中身が空だと、
  押しても何も現れないボタンを出すことになる

## 表示のために丸めた値を、判断に使わない

同じ量に「保存・比較のための値」と「画面に出すための丸めた値」の 2 つがあるとき、判断のほうへ
丸めた値を渡すと、**比較が必ず片側へ転ぶ**。しかもテストの期待値を丸まった形（整数など）で
手書きしていると、そのテストは緑のまま通る。

#164 では、JSON へ書くのが端数のある実長（`pcm.len() / 16000` の f64）なのに、上書きしてよいかの
比較には表示用に秒へ切り捨てた `Duration` を渡していた。同じ音源をやり直しても常に
「前のほうが長い」と判定され、**その比較を入れた目的そのもの**（やり直しでも途中結果を伏せ続ける）
が効かなくなっていた。レビューで 2 周続けて同じ場所の修正を外している。

- 判断に渡すのは**保存する値そのもの**。丸めるのは表示の直前だけにする
- 丸めた値と丸める前の値を**同じ変数で兼ねない**（用途が違うなら名前も分ける）
- テストの入力は**実際に書かれる形**にする。整数で試すと、この間違いを丸ごと見逃す

## 安全判定の `all()` は、空を渡されたときにどちらへ倒れるか決める

`items.iter().all(…)` は**空だと真**になる（空真）。判定が「揃っているか」「検証を通ったか」の
たぐいなら、**取り落とした結果がいちばん危険な答えに化ける**——#175 の
`transcript::sources_shortfall`（#175 当時は `all_sources_are_complete`）は、音源を 1 つも渡さないと「在る音源ぶんが全部揃って
いる」＝欠けた文字起こしを完成品として画面に出す側へ落ちていた。壊れ方として一番ありがちな
「対象を取り落とす」が、一番まずい答えに直結する。

- 空をどう扱うか**を書く**（`!items.is_empty() && items.iter().all(…)`）。書かずに空真へ任せない。
- 空が本番に来ない設計なら、それこそ**テストで留める**。来ないぶん、壊しても症状が出ない。
- 「本文だけ要る」ような呼び出しのために空を渡せる形（`&[]`）を残さない。読み口を割って、
  空を渡す書き方が本番に 1 つも無い状態にする（`load_segments` / `load_transcript`）。

## 値を 2 度読まず、書いた値そのもので分岐する

同じ事実を「保存する構造体の欄」と「手元の変数」の両方から読むと、**片方だけ書き換えた食い違い**
（JSON には「完成」と書いたのに、呼び出し側へは「途中結果」を返す）を書けてしまう。
#175 の `transcribe_file` は `if complete` を `if result.complete` に変えて、分岐が必ず
**保存する値**を見るようにした。副産物として、欄を定数へ固定する壊し方が「変数が未使用」で
CI（`-D warnings`）に当たるようになる。

## 真偽値 2 つで場合分けするなら、組にして網羅で書く

「どちらへ倒すか」が 2 つの真偽値で決まるとき、否定を並べた早期 return を重ねると**書いた本人が
数え上げたつもりの組み合わせが 1 つ抜ける**。#176 の `transcribe::write_decision` は
「在るほうが途中で終わっているか」「新しいほうが途中で終わっているか」の 2 つで分けていたが、
**もう 1 つの軸（抜けているか）**を条件に入れ忘れ、`StopsPartwayWithGaps` が黙って長さの比較へ
落ちていた——doc には「読み飛ばしを跨いで比べない」と書いてあったのに、実装がそれを守って
いなかった。

- 場合分けは **`match (a, b)` の網羅**で書く。ワイルドカードを置かない。組み合わせを足したら
  コンパイルが割れて、扱いを書くまで通らない。
- **各腕に「なぜその答えなのか」を書く**。同じ答えでも理由が違うなら腕を分ける（#176 の
  `(HasGaps, HasGaps)` は「新しいほうが届いたから書く」ではなく「残量で比べる」）。
- テストは**結論が変わる値**で書く。#176 では在る側の長さを新しい側より長くしていたため、
  比較へ落ちるミューテーションでも同じ答えになり、穴が素通りした。

## 1 つの真偽値に 2 つの問いを相乗りさせない

名前が答えている問いと、使っている場所が聞いている問いがずれると、**どちらの読みが正しいかが
コードから決まらない**。#176 の `kept_other_sources` は「この実行が読める文字起こしを書けたか」
（失敗の理由に使う）なのに、「セッションに開いて読む行が在るか」の判定にも使われていた。
書かずに保存物を守った音源はディスクに行が在るのに前者では false なので、全音源を守ったジョブで
食い違いが握り潰され、画面が「Transcribed」と言い続けた。

- 問いが違うなら**変数を分ける**（`kept_other_sources` / `has_readable_lines`）。片方の doc に
  「こちらの意味では使わない」と書き添える。
- 相乗りは**コメントどうしの食い違い**として先に現れる（片方は「この実行が書いたもの」、
  もう片方は「セッション単位で見る」）。レビューで両方のコメントを並べて読む。
