# 実装ルール: エラーハンドリング

レビューで繰り返し出やすい、エラーの扱いに関する規約。

## Result を握りつぶさない

- `let _ = result;` で `Result` を捨てない。
- `?` で伝播できる箇所は伝播する。
- `?` で伝播できない箇所（`'static` クロージャ、イベントループのコールバック等）では、
  最低限 `eprintln!` などで失敗をログに残す。黙って捨てない。

```rust
// NG
let _ = window.hide();

// OK
if let Err(err) = window.hide() {
    eprintln!("ウィンドウの非表示に失敗した: {err}");
}
```

- **後始末・失敗回復の経路でも握りつぶさない**。開始失敗時のロールバック（一時ファイル削除、
  スレッドの join、ストリーム停止など）の `Result` も `let _ =` で捨てず、最低限ログに残す。
  主たるエラーを返す途中でも、後始末の失敗は別途気づけるようにする。
  共通化できるなら後始末ヘルパに集約し、その中でログする。

## ロック（Mutex）を停止・後始末で閉じるときは poison でも確実に行う

writer スレッドへ送る `Sender` を `Arc<Mutex<Option<Sender>>>` 等で共有し、停止時に `None` にして
チャネルを閉じる設計では、`Mutex` が poison（ロック保持中にパニック）していても**必ず閉じる**。
`if let Ok(g) = m.lock()` だと poison 時に閉じ漏れ、`recv` が終わらず `join` がハングする。
`lock()` の `Err` から `PoisonError::into_inner()` でガードを取り出して処理する。

```rust
let mut guard = match shared.lock() {
    Ok(guard) => guard,
    Err(poisoned) => poisoned.into_inner(), // poison でもガードを取り出して確実に閉じる
};
*guard = None;
```

## 永続化に成功してから in-memory / UI を更新する

保存（ファイル書き込み・設定の永続化など）を伴う更新では、**永続化が成功してから**
メモリ上の状態や画面表示を更新する。先に更新して保存失敗をログするだけだと、「画面・メモリは
新しい値なのにディスクは古い」という不整合になり、次回起動で戻ってユーザーを混乱させる。

```rust
// NG: 先に反映してから保存（失敗すると表示とディスクが食い違う）
state.value = new_value;
if let Err(err) = state.save() { eprintln!("保存失敗: {err}"); }
ui.set_value(new_value);

// OK: 候補を保存し、成功したときだけ反映する
let mut candidate = state.clone();
candidate.value = new_value;
if let Err(err) = candidate.save() {
    eprintln!("保存に失敗したため変更しない: {err}");
    return;
}
ui.set_value(candidate.value);
state = candidate;
```

## expect / unwrap は初期化時の不変条件だけ

- 本番経路の `unwrap()` / `expect()` / `panic!()` は避ける。
- 初期化時など「ここでは必ず成功する」と言える箇所に限り `expect("理由")` を使い、
  **なぜ成功すると言えるのか**を理由に書く。

```rust
// main は常にメインスレッドで動くため成功する、という不変条件を理由に書く
let mtm = MainThreadMarker::new().expect("main は常にメインスレッドで動くため成功する");
```

## 手編集される設定 TOML のフィールドは寛容にデシリアライズし既定へ丸める

設定ファイル（`config.toml`）は手編集されうる信頼境界の外。フィールドを `u32` や `String` で直接
受けると、負値・型の範囲外・型不一致（数値フィールドに文字列、文字列フィールドに数値等）のときに**その 1 フィールドの不正でファイル全体のパースが
失敗**し、`load()` が丸ごと既定へフォールバックして無関係な設定（保存先・登録アプリ等）まで
失わせる。当該項目だけを既定へ丸め、他フィールドを巻き添えにしないこと。

- `#[serde(deserialize_with = "...")]` で緩く受け、`toml::Value` 経由で読んで妥当なら採用、
  さもなくば既定にする。ついでに有効範囲へ丸めれば「デシリアライズ後は常に範囲内」という
  不変条件が構造体に立ち、使う各所での丸め漏れを防げる（丸め口を増やさない）。
- `#[serde(default = "...")]` は**フィールド欠落**に効き、`deserialize_with` は**存在するが
  不正な値**に効く。旧 config 互換（欠落）と手編集耐性（不正値）は別物なので両方指定する。
- TOML 整数は i64。i64 も超える極端値はこの関数に届く前に TOML パースで失敗する。現実的な値
  では起きないが、doc で「i64 超は全体フォールバック」と正直に書き、過大な保証を書かない。
- 数値だけでなく **文字列フィールドも真偽値フィールドも同じ**（`as_str()` / `as_bool()` が
  取れなければ既定へ）。UI から設定できるフィールドを追加するときは、必ずこの寛容デシリアライズを
  セットで付ける。**トグル（`bool`）を忘れやすい**——`#[serde(default)]` だけでは型不一致を
  救えず、`auto_summarize = "on"` のような手編集 1 行でファイル全体が既定へ落ちる
  （`deserialize_bool_or_false` を通すこと）。

```rust
#[serde(default = "default_debounce_secs", deserialize_with = "deserialize_debounce_secs")]
pub auto_stop_debounce_secs: u32,

fn deserialize_debounce_secs<'de, D>(d: D) -> Result<u32, D::Error>
where D: serde::Deserializer<'de> {
    let v = toml::Value::deserialize(d)?;
    let secs = v.as_integer().and_then(|n| u32::try_from(n).ok()).unwrap_or(DEFAULT_DEBOUNCE_SECS);
    Ok(clamp_debounce_secs(secs)) // 常に [MIN, MAX] を返す
}
```

## 状態を持つエッジ検知は、監視を止めた区間の後で必ず再プライムする

「非稼働→稼働」等の立ち上がりを前回値との差分で検知するポーリングでは、負荷やロジックの都合で
一定区間だけ監視（照会）を止めることがある（例: 録音中は開始検知の照会を止める）。このとき前回値が
その区間の開始時点で凍結される。監視を再開する前に**前回値を現在値へ取り込み直す（再プライムする）**
こと。さもないと、止めている間に変化した対象を再開直後に「立ち上がり」と誤検知して誤発火する。

- 再プライムは**区間を終えるすべての経路**で行う。片方の経路（例: 自動停止）だけで再プライムし、
  別経路（例: 手動停止）で忘れると、その経路の後だけ誤発火する。停止処理を集約するか、各停止経路で
  同じ再プライム関数（例: `reset_after_stop`）を必ず呼ぶ。
- 再プライムは「現在値を前回値に入れて、その回は発火しない」動作にする（オプトイン監視の初回
  プライムと同じ考え方。[[security.md]] の「オプトインの監視は監視自体を設定でガードする」も参照）。

## 縮退（フォールバック）経路も、決定的にテストできるなら 1 ケース入れる

エラー時に「機能を諦めて続行する」縮退経路（例: ロック取得不可でガード無しで起動続行、モデル
取得不可でスキップ）は、正常系ほど注目されずテストが抜けやすい。しかしそこが壊れると「安全に
縮退」どころか起動不能・パニックになりうるため、**決定的に再現できる縮退経路は 1 ケースだけでも
テストする**。

- 環境依存で再現困難な入口（`ProjectDirs` 取得不可など）は、判定本体を引数を取る内部関数へ切り出し
  （例: `acquire_at(path)`）、決定的に失敗させられる入力（存在しない親ディレクトリ配下のパス等）で
  縮退バリアントを検証する。
- 再現が本当に困難な分岐まで無理にテストしない。「決定的に書けるのに抜けている」ものだけを埋める。

## ロード系の関数は、失敗時に前の対象の状態を残さない

「対象を差し替える」関数（再生ファイルのロード等）が失敗時に早期 return すると、ハンドルに
**前の対象の状態**（パス・キュー・長さ等）が残る。後続の操作（seek・再生）がその stale な
状態を参照すると、「画面は新しい対象、動作は前の対象」という食い違いになる（例: セッション B の
ロード失敗後にトランスクリプトをクリックすると前のセッション A の音声でシークされる）。

- 差し替えの冒頭で自身の状態を空（`None` / clear）へリセットしてから新しい対象を開く。
  失敗しても「何もロードされていない」という一貫した状態に落ち、後続操作は `path` が
  `None` なら何もしない既存のガードで自然に安全側へ倒れる。

## 共有状態の完了待ちポーリングには必ず上限を設ける

「他スレッドが処理中なら共有状態を見ながら sleep して待つ」ループは、担当スレッドが結果を
記録する前に異常終了すると状態が「処理中」のまま残り、**待機側が永久に固まる**。待機側が
逐次ワーカー（文字起こし等）だと、以後のジョブすべてが黙って止まる。

- 待機ループには deadline（処理全体のタイムアウトより長い上限）を設け、超過したら Err で
  抜けて呼び出し側の再試行に任せる。
- 上限は「正常な待機を打ち切らない」長さにする（例: DL 全体タイムアウト 120 分に対し 130 分）。

## 失敗しうる操作の前に手放した状態は、失敗経路で巻き戻す

「先にリソースを手放してから外部操作する」順序が必要な場合（例: 削除前の
`player.unload()` — 開いたままのハンドルがゴミ箱移動を妨げる OS があるため）、
外部操作が失敗して早期 return する経路で**手放した状態を積み直す**（best-effort で可）。
巻き戻しが無いと「UI は操作可能に見えるが実体は空」という不整合が残り、
以後の操作が黙って効かなくなる（in-out 保存失敗の巻き戻しと同じ趣旨）。

## 失敗しうる操作のために増やした状態も、失敗経路で巻き戻す

「手放した状態を戻す」の裏返し。ある操作を成立させるために**先に状態を増やす**（再生キューへ
ソースを積み直す、一時ファイルを置く、リスナーを登録する等）場合、その後の操作が失敗して
`Err` を返す経路で、増やした状態を元に戻す（`AudioPlayer::seek` が実例。シーク前にキューへ
積み直し、`try_seek` 失敗時は `clear()` で戻す）。

- 戻さないと「失敗を返したのに副作用だけ残る」状態になる。上の例では、終端後は一時停止状態で
  ないため、積んだままにすると**シークに失敗したのに先頭から鳴り出す**。
- 「増やしたのはこの呼び出しか」をフラグで持ち、元から在った状態を壊さないようにする。

## 外部クレートの `Ok` は「何もしなかった」を含むことがある

外部 API の成功が「要求どおり実行した」を意味するとは限らない。前提が満たされないときに
黙って何もせず `Ok` を返す実装がある（rodio の `Player::try_seek` はキューが空だと即 `Ok`。
シーク対象が無いのに「シークできた」と伝わる）。

- 呼ぶ前に前提（対象が在るか）を自分で確認し、満たないなら自分で `Err` を返す。
- ラッパの戻り値が呼び出し側の分岐（表示更新の可否など）を決めるときは特に重要。
  「Ok なら反映してよい」という契約を、ラッパ側で成立させる。

## 表示を「状態のポーリング」に任せているなら、ポーリングを止める条件に注意する

UI の表示を 100ms tick のようなポーリングで駆動している設計では、tick が**表示の自己修復**も
担っている（コールバック側が更新し忘れても、次のティックが実状態で塗り直す）。ここに
「◯◯のときは駆動しない」というゲートを足すと、その自己修復も同時に失われる。

- ゲートを足すときは、**ゲートが立つすべての経路**で表示が確定済みかを確認する
  （`is_loaded()` ゲート追加時、削除失敗＋積み直し失敗の経路だけ確定漏れがあった）。
- 逆に「コールバックで表示を更新しない」縮退を作るときは、tick が上書きしないかを確認する
  （`docs/rules/slint.md` の「『失敗したら表示を更新しない』は、ポーリング tick の上書きまで
  考える」と対）。

## `chrono::DateTime::from(SystemTime)` を使わない

`impl From<SystemTime> for DateTime<Utc>` は内部で `unwrap` する（chrono の表現範囲は
±約 262143 年）。ファイルの更新時刻はファイルシステム・同期ツール・手編集から来る**信頼境界の
外**の値なので、範囲外が来た瞬間にパニックする。UI スレッドで呼んでいればアプリごと落ちる。

`duration_since(UNIX_EPOCH)` → `i64::try_from` → `DateTime::from_timestamp` と辿り、どこかで
外れたら表示を諦める（`main::summary_footer_text` が実例）。
