# 実装ルール: UI デザイン

画面を作る・作り直す実装に入る前の手順。デザインは **Claude Design** で作り、その成果を正として
実装する（実装者が見た目まで決めない）。

## デザインが要るかを最初に判定する

**要る**:

- 画面を新しく作る
- 既存画面のレイアウト・情報の並び・状態の見せ方を作り直す
- 新しい種類の UI 要素を持ち込む（これまで無かった部品・操作）

**要らない**（やると遅くなるだけ）:

- 表示文言の修正
- 既存の並びに同じ形の項目を 1 つ足す
- 内部リファクタ、「見た目も挙動も変えない」と明記された issue

迷ったら issue の受け入れ条件を見る。「レイアウト」「配色」「状態の見せ方」に触れていれば要る。

## すでにデザインがあるなら、読んでから実装する

issue の参照欄に Claude Design のリンクがある場合:

1. **`DesignSync` で中身を読む**（`get_project` → `list_files` → `get_file`）。プロジェクト ID は
   URL の `/design/p/<id>` の部分、ファイル名は `?file=` の値。
   共有リンクは `WebFetch` では 403 になるので使わない。`DesignSync` が使えない場合は、
   ユーザーに `/design-login` の実行を依頼する。
2. **issue 本文とデザインの食い違いを洗い出し、ユーザーへ報告してから**実装に入る。issue は
   デザインより前に書かれていることが多く、採用しなかった構成・古い用語・想定のままの寸法が
   残っている（#127 では「固定フッタ」がデザインに存在せず、#128 では Summary タブが本文から
   抜けていた）。
3. **デザインが前提にしていて実装に無い機能**を列挙し、この issue でやるか別 issue に送るかを
   決める。デザインは実装の制約を知らないので、たいてい何か増えている（#128 の一覧検索、
   #140 の Cancel / Retry、ダウンロードの再開など）。
4. デザインで決まった寸法は、`.slint` の `min-*` / `preferred-*` と `src/main.rs` の定数の
   **両方**へ反映する（`docs/rules/slint.md`）。

## 無いなら、実装を始めずにユーザーへ依頼する

**コードを書き始めない。** デザイン無しで書くと、後からデザインが来たときに同じ画面を二度
作ることになる。`za:goal` の通し実行でも、ここは「前提の不成立」として停止してよい。

依頼するときは、**そのまま Claude Design へ貼れるプロンプトを添える**（ユーザーに文面を
考えさせない）。

### プロンプトに書くこと・書かないこと

**書く**: 何を出す必要があるか・何が破綻してはいけないか・技術的に何ができないか。

**書かない**: レイアウト、配色、余白、使う部品の種類、情報の並び順。それを決めるのが
デザインの仕事で、こちらが指示すると自分の思いつきをなぞらせることになる。末尾に
「並び順・まとめ方・装飾の強弱・寸法はすべて任せる」と明記する。

Claude Design はリポジトリを読めないので、**プロンプトだけで自己完結**させる。既存の
ビジュアル資産（アプリアイコン等）は「こうしろ」ではなく「こうなっている」という事実として
書き、活かすかどうかは委ねる。

### 雛形

issue とコードを読んで埋める。「画面に出る情報と操作」は `.slint` のプロパティ・コールバックと
Rust 側の状態から**網羅**すること（ここが漏れるとデザインも漏れる）。

```markdown
{プロダクト名} の{画面名}を{新設 / 再設計}したい。

## プロダクトの前提
- 何のアプリか、どのプラットフォームか、どういう使われ方をするか（2〜4 行）
- 誰が使うか、この画面をいつ開くか
- 既存のビジュアル資産があれば事実として書く

## この画面の役割
{1〜2 行}

## 画面に出る情報と操作（現状の全項目）
{項目名・取りうる値・件数の幅・操作の一覧を網羅する}

## 満たしてほしいこと
- 情報の従属関係や優先順位で、読み取れる必要があるもの
- 長い文字列・0 件・大量件数で破綻しないこと
- ライト／ダーク、最小サイズなどの要件

## 技術的な制約
- 実装は Slint（QML に近い宣言的な UI ツールキット）。Web ではないので CSS 前提の効果は使えない
- 標準ウィジェットは OS の配色のままで、アプリのトークンに追従しない（`docs/rules/slint.md`）
- 自作の操作部品を入れる場合、キーボード・フォーカス・アクセシビリティを自前で実装する必要がある
- 持っている素材（フォント・画像）の有無

## 欲しい成果物
- 画面のデザイン（ライト／ダーク）
- 状態のバリエーション（空・エラー・進行中・最長文言など、具体的に列挙）
- 寸法の目安

情報の並び順、まとめ方、装飾の強弱、寸法はすべて任せる。上に書いたのは「何を出す必要が
あるか」であって「どう見せるか」ではない。
```

### 上がってきたら

リンクを **issue の参照欄へ追記してから**実装に入る（次に読む人が辿れるように）。あわせて、
上の「すでにデザインがあるなら」の 2〜4 を行う。
