# 実装ルール: セキュリティ

## 機微データのファイルは所有者限定パーミッションで作る

録音データなど機微なファイルは、既定の umask 任せ（多くの環境で 0644 になり他ユーザーが
読める）にせず、Unix では所有者のみ読み書き可（0600）で作成する。

**自分で `OpenOptions` を組まず、`crate::private_file` を使う**（録音・ミックス音声・
文字起こし JSON・議事録 Markdown はすべてここを通る）。

```rust
crate::private_file::write(path, data)?;          // 一括で書く
let mut file = crate::private_file::create(path)?; // 複数回書き分ける
```

- `OpenOptions::mode` は**ファイル作成時にしか効かない**。既に 0644 のファイルが在ると
  （`cp -r` した・バックアップから戻した等）、上書きしてもそのモードが残る。文字起こしの
  やり直し・議事録の再生成のように**既存ファイルを上書きする経路がある**ので、
  `private_file` は開いた後に `set_permissions` で揃え直している。自前で書くとここが漏れる。
- 権限を表現できないファイルシステム（外付けの exFAT、SMB/NFS 等）では `set_permissions` が
  失敗しうる。そこは書き出しごと失敗させず、ログに残して続行する（落としても守れるものが無い
  一方、後処理がまるごと失敗する）。
- 非 Unix は OS 既定（Windows 対応時に ACL 等を別途検討）。

## 機微データを置くディレクトリも所有者限定で作る

録音セッションのディレクトリのように**機微なファイルを入れるディレクトリ**は、ファイルを
0600 にしてもディレクトリが緩い（umask 既定で 0755）と中身の一覧が他ユーザーに漏れる。
新規作成するディレクトリは Unix で 0700（所有者のみアクセス可）にする。`create_dir_all` は
mode を指定できないため、`DirBuilder` を使う。

```rust
let mut builder = std::fs::DirBuilder::new();
builder.recursive(true); // 親が無ければ作る（create_dir_all 相当）
#[cfg(unix)]
{
    use std::os::unix::fs::DirBuilderExt;
    builder.mode(0o700);
}
builder.create(dir)?;
```

- `mode` は新規作成するディレクトリにのみ効く（既存ディレクトリの権限は変えない）。
- 単なる `std::fs::create_dir_all(dir)` は umask 任せになるため、機微ディレクトリには使わない。

## 信頼境界の外から来る値は、使う側でその旨を明示する

設定ファイル（手編集されうる）由来のパスなどは信頼境界の外。そのまま I/O に使う場合は、
「なぜそのまま使ってよいか」をコメントで残す（例: ユーザー自身が選んだ保存先であり、検証は
設定 UI 側の責務）。後から読む人が「検証漏れ」と「意図的」を区別できるようにする。

## オプトインの監視は「動作」だけでなく「監視自体」を設定でガードする

プライバシーに関わるセンシティブな監視（全プロセスの音声使用状況の走査など）をオプトイン
（既定 OFF）で入れるとき、設定 OFF でも監視だけは常時走らせて「発火（録音開始など）」の側だけを
設定で止める、という実装にしない。ユーザーが無効化している間は**監視処理そのものを行わない**
（＝設定 ON かつ対象が空でないときだけ照会する）。常駐アプリのアイドル負荷を抑える意味もある。

- 例: `take_activated(triggers, enabled)` の冒頭で `!enabled || triggers.is_empty()` なら
  システム照会をせず即 `false` を返す。発火条件（`config.borrow().auto_record_on_x`）を
  照会の**後**に評価すると、OFF でも毎回照会が走ってしまう。
- 監視を間欠化すると立ち上がりエッジ判定の前回値が古くなる。OFF→ON の最初の照会では現在値を
  取り込むだけにして（`primed` フラグ等）、既に稼働中の対象を遡って発火させない。

## 外部からの大容量ダウンロードは「検証・原子的配置・タイムアウト・上限」を揃える

モデル等の大きなファイルを HTTPS で取得するときの定型。実装は共有基盤
`src/model_download.rs` にあり、モデル種別ごとのカタログ（`src/whisper_model.rs` の
`CATALOG` 等）は `ModelSpec`（種別ラベル・ID・表示名・説明・サイズ・保存ファイル名・URL・
SHA-256）を並べるだけでよい。
**新しい種別のモデルを足すときは、この定型を書き直さず共有基盤に載せる**:

- **完全性**: 既知の SHA-256 をハードコードして受信内容を検証する（TLS と二重の防御）。
  検証前のデータが成果物として使われる経路を作らない。
- **原子的配置**: 一時ファイルへ書き、検証に通ってから `rename`。一時ファイル名は
  **プロセス固有**（PID 付き等）にする。多重起動で同名の一時ファイルへ同時に書くと、
  ハッシュは各自の受信ストリームで計算されるためファイル破損を検知できない。
  実装は `src/atomic_replace.rs` の `PartFile` に寄せる（命名・rename・後始末を 1 箇所に持つ）。
- **一時ファイルの後始末**: 失敗時だけでなく**パニックで抜けたときも消す**（`Drop` で消す番人に
  する）。数 GB の一時ファイルが、ユーザーが辿らない場所に残ると気づかれない。Drop が走らない
  終わり方（`abort`・強制終了）で残ったものは、起動時に「最終更新から十分に経ったもの」だけを
  掃除する（`sweep_orphaned_parts`）。**mtime で判定**すれば、書き込み中のファイルは自然に
  対象外になり、多重起動した別プロセスの取得も壊さない（PID の生存確認は要らない）。
  掃除は**通常ファイルだけ**を対象にし（シンボリックリンクを辿って別の場所を判定しない。
  掃除するディレクトリ自身がリンクの場合も辿らない。どちらの判定も `sweep_orphaned_parts` に
  持たせ、掛け先を増やす人が忘れられないようにする）、対象は**アプリが名前と構造を決めている
  場所**に限る: アプリのデータディレクトリ（起動時に掃除。宛先名は絞らない）か、Recordings
  ウィンドウの一覧に出たセッションディレクトリの直下（ユーザー操作の契機で掃除。**ユーザーが
  中身を置ける場所なので宛先名まで絞る**）。ユーザーが選んだ保存先を**丸ごと**走査はしない。
  ユーザーの領域から消す場合は、消すのが「成果物ではなく書き損じの断片」であること
  （＝ゴミ箱へ送らずに消してよい理由）を doc に残す。宛先名で絞るときは、**そのファイルを書く
  モジュールの定数**を引く（文字列の写しを置くと、書き手が名前を変えたときに掃除だけが静かに
  効かなくなる。取りこぼしはコンパイルもテストも通ってしまう）。
  ログには**ファイル名だけ**出す（データディレクトリのフルパスはユーザー名を含む）。
- **タイムアウト**: ureq の既定は無期限。逐次ワーカー上で無応答接続に当たると以後の処理が
  恒久に止まるため、connect/recv を明示設定する（大容量の body は余裕を持った値に）。
- **サイズ上限**: 既知サイズ＋余裕で受信を打ち切る（想定外の応答でディスクを埋めない保険）。
- **空き容量**: 受信を始める前に保存先の空きを確認し、足りなければ受信せずに失敗する
  （「受信上限＋残す余白＋並走している他の取得の残り」で見る）。埋め尽くしてから ENOSPC で
  落ちると、帯域を数 GB 無駄にしたうえに録音の書き出しまで巻き込む。空きが読めないときは
  確認を飛ばして続行する（受信上限と ENOSPC が最後の砦）。**同時ダウンロード数の上限は
  持たない**判断とその根拠は `request_download` の doc（#120）。
- **担当の後始末**: 取得を引き受けた区間は番人（`DownloadGuard`）で囲み、結果を記録せずに
  抜けても状態を `Downloading` のまま残さない。残すと、そのモデルは二度と取得されず
  （`request_download` が早期 return する）、空き容量の見積もりも恒久的に過大になる。
- **オプトイン**: 通信はユーザーが機能を有効化したときだけ発生させ、UI・README に
  接続先と「機微データは送信しない」ことを明示する。
- **二重取得の防止**: 取得状況は共有の状態マップ（`ModelDownloader`）でモデル ID をキーに
  管理し、check-and-set で担当を 1 スレッドに絞る。**ID と保存ファイル名は種別をまたいで
  一意**にすること（ID が衝突すると状態が混ざって表示と取得が黙って壊れ、ファイル名が衝突
  すると存在確認が他種別のファイルを掴んで検証なしに「取得済み」を返す）。カタログを足したら
  `model_download::REGISTERED_CATALOGS`（カタログ集合の唯一の正。取得済みモデルの列挙も
  横断の一意性検査もここを読む）に 1 行足す。これだけで
  静的な健全性検査（ID・ファイル名の重複、SHA-256 の形式、サイズ、パス要素を含まない
  ファイル名）と横断の一意性がテストで効く。

## 信頼境界外ファイルの読み込みは、上限を読み込み自体に掛けてから中身をログに出さずパースする

保存先ディレクトリ配下の生成物（文字起こし JSON 等）は、ユーザーが手で置換しうる信頼境界外の
入力。読む側では次を揃える（`src/transcript.rs::read_guarded` が実例）:

- **サイズ上限は読み込みそのものに掛ける**: `fs::metadata` の事前判定だけでは、判定後の
  差し替え（TOCTOU）や FIFO 等の非通常ファイル（len=0 に見えて読み終わらない）を防げない。
  `File::open` → ハンドルの `metadata()`（fstat）で `is_file()` を確認し、
  `Read::take(MAX + 1)` で読んで `limit() == 0` なら上限超過として弾く。
- **パースエラーの本文をログに出さない**: `serde_json::Error` の `Display` は型不一致時に
  **JSON 中の値をそのまま**含める（例: `invalid type: string "発話内容..."`）。録音由来の
  機微データがログへ漏れるため、`err.line()` / `err.column()` など位置情報だけをログする。
- **ログにはファイル名だけ含める**: どのファイルで起きたかは調査に必要だが、フルパス
  （保存先の機微情報）は出さない（`path.file_name()` を使う）。

## 外部クレートのエラー型はフルパスを含みうる — ログへそのまま流さない

`trash::Error` のように、外部クレートのエラー型は `Display` / `Debug` にフルパスや
コマンドラインをそのまま埋め込むことがある。`eprintln!("...: {err}")` の定型でも、
エラー型が保存先の機微情報を運んでくればログ方針（ファイル名のみ）に違反する。

- 外部クレートのエラーをログへ出すときは、まずその `Display`/`Debug` 実装を確認する。
- パスを含みうる場合は、バリアント名や OS エラーコードなど**パスを含まない要約**へ
  変換してから出す（例: `trash_error_kind`）。位置の特定はセッション名
  （日時ディレクトリ名）だけを添える。

## macOS のゴミ箱移動は NsFileManager 方式を明示する

`trash` クレートの macOS 既定（Finder 方式）は osascript の子プロセスで Finder を
Apple Events 操作するため、(1) 初回に Automation 権限プロンプトが出て拒否されると
以後の削除が全て静かに失敗し、(2) フルパスが子プロセスの引数に渡る。ゴミ箱移動には
`TrashContext` + `DeleteMethod::NsFileManager` を明示する（追加権限・子プロセス不要。
`move_recording_to_trash` 参照）。

## 一時ファイルの書き手を増やしたら、掃除の対象にも足す

`atomic_replace::PartFile` で書くようにした宛先は、`recordings::SWEPT_PART_DESTS` にも足す。
足し忘れると、**その断片だけどの経路でも回収されない**。#162 で `mix.mp3` を原子的置換へ変えた
とき、実際に穴が空いた——1 時間の録音なら数十 MB の発話が、ユーザーの気づかないまま録音
フォルダに残り続ける形だった。

掃除は宛先名で絞っているので（ユーザーが置いたファイルを消さないため）、書き手が増えても
自動では追わない。**新しい `PartFile::for_dest` を書いたら、対で一覧を確かめる。**
