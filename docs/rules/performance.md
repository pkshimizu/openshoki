# 実装ルール: パフォーマンス

レビューで繰り返し出やすい、常駐アプリのメモリ・CPU に関する規約。

## GB 級になりうる中間バッファは move で渡し、重い処理の前に解放する

音声 PCM のような「入力長に比例して GB 級になりうるバッファ」を多段変換（デコード→
ダウンミックス→リサンプル等）するときは、各段階へ **`Vec` を move で渡し**、次の段階の
出力を作った時点で前段のバッファが drop されるようにする。`&[T]` で借用させて呼び出し元の
変数に持たせたままにすると、最後の重い処理（推論など、秒〜分オーダー）の間じゅう全段階の
バッファが生存し、ピークメモリが数倍になる。

- パススルー（変換不要）の段階は move で受けてそのまま返せば、コピーもゼロになる
  （`&[T]` 受けだと `to_vec()` の全量コピーが要る）。
- 変換ループでは中間チャンクを介さず、出力 `Vec` の末尾へ直接書く（`resize` + スライス書き込み）。
  全量を 2 回なめる memcpy を避ける。

## 大きなリソース（ML モデル等）はジョブ単位でロードし、対象が無ければロードしない

数百 MB 級のリソース（whisper モデル等）は、アイドル常駐させず**ジョブ内で 1 回ロードして
ジョブ内の複数対象に使い回す**。ジョブの対象が空ならロード前に return する。

## UI コールバックで「入力長に比例する同期処理」をしない

Slint のコールバック（＝イベントループ）から呼ぶ処理に、**対象の長さに比例して伸びる同期
処理**を置かない。長い録音でウィンドウが固まる。録音は数時間になりうるので「短い入力では
体感できない」は根拠にならない。

- 実例: シークのフォールバックに使っていた `Source::skip_duration` は目的位置までの全サンプルを
  同期デコードする（release の実測で 20 分の MP3 の終端へ約 580ms）。同じ用途の
  `Decoder::try_seek` はフレームヘッダ走査で ms 級（同条件で約 2.7ms）。
- 比例する処理が避けられないなら、録音直後のバックグラウンドワーカーへ移す
  （`mixdown.rs` のミックス生成と同じ考え方）か、機能を諦めて縮退させる。
- 「比例するが桁が小さい」ものは許容してよいが、**どの桁か**を実測して doc に残す。

## 重い読み込みを別スレッドへ出すときは、書き込む経路を 1 本に絞る

UI を固めないために読み込みをスレッドへ出すと、**同じ表示を書く経路が増える**。#152 では
「選択時」「tick の完了反映」「読み込み結果の反映」の 3 つが `set_segments` を書いていて、
順序の保証が無かった。

そこで起きるのは、次の順序で**完成した中身が消える**こと:

1. 文字起こし中の録音を選ぶ → スレッドが走り出す（このとき JSON はまだ無いので、読むと空）
2. 数秒かかる音声の読み込みの最中に、文字起こしが完成する
3. tick がそれを拾って表示する（画面に文字起こしが出る）
4. スレッドの結果（**空**）が届いて上書きする

しかも tick は「実行中 → 完了」の遷移でしか動かないので、**選び直すまで直らない**。

守り方は 2 つ:

- **書く経路を 1 本にする**。tick は表示を書かず、世代を進めて読み込みをやり直す。
- **世代で古い結果を捨てる**。世代は「選択が変わったとき」だけでなく、**中身がディスク上で
  変わったとき**にも進める（そこが抜けると上の順序で負ける）。

あわせて、重い処理に入る前に世代を確認して降りられるようにする。連打したぶんだけ数百 MB を
読み切るのは、いま見たい録音の読み込みを自分で遅くする。
