# 実装ルール: テストの書き方

テストで繰り返しつまずく前提を集める。UI（Slint）操作の検証は
[[slint.md]] の「UI 操作の検証は `tests/` のテストバックエンドで…」を参照。

## 出力デバイスに依存せず再生ハンドルを組む

`AudioPlayer`（`src/player.rs`）は本番では既定の出力デバイスを開くが、CI のランナーには
出力デバイスが無い。テストは `rodio::mixer::mixer()` で作ったミキサーに `AudioPlayer::connect`
で繋ぐ（`connect` の doc コメント参照）。これで状態遷移（ロード・再生・一時停止・停止・
手放し・シーク）をデバイス無しで検証できる。

- **出力を引く役を必ず用意する**: rodio は「出力側がサンプルを引いたとき」に再生位置を更新し、
  キューのクリアも進める。引かないと位置が動かず、`unload` / `stop`（内部でクリアの完了を待つ）は
  **戻ってこない**。
- **引く役の置き方は 2 通り**。クリアの完了待ちを含む操作を呼ぶなら**別スレッド**
  （`FakeOutput`）、位置の進み方だけを見るなら**テストスレッド自身が引く同期ドライバ**
  （`ManualOutput`）。後者は sleep が要らないぶん決定的なので、選べるなら同期ドライバにする。
- **`load` も内部で `unload`（＝クリアの完了待ち）を呼ぶ**。同期ドライバで `load` を呼べるのは
  キューが空のとき（新品ハンドルへの初回ロード）だけで、2 回目の `load` は無期限に戻らない
  （テスト単位のタイムアウトが無いため、CI ではジョブのタイムアウトまでハングする）。
- **引く役はテストの終わりまで保持する**。drop すると引くのが止まり、以後の待ちは必ず
  タイムアウトする（`let (player, _output) = ...` の `_output` を消さない）。

## 別スレッドの反映を待つときは上限つきポーリングにする

上の疑似オーディオスレッドのように、状態が別スレッド経由で反映されるものは、固定 sleep で
待たない（CI の負荷で簡単に偽陽性・偽陰性になる）。「条件が満たされるまで待つ」ヘルパを使い、
必ず上限を設けて超えたら失敗させる（`docs/rules/error-handling.md` の「完了待ちポーリングには
必ず上限を設ける」と同じ趣旨）。タイムアウトのメッセージには上限値と第一容疑者を書く。

## 配線（部品どうしの繋ぎ）は、繋いでいる関数に継ぎ目を入れてテストする

部品を単体でテストしていても、**部品を繋いでいる関数**（ネットワーク・ディスクに触るので
テストから呼べないもの）が検査対象から漏れることがある。そこに不変条件が置いてあると、
壊してもテストが全部緑のまま通る。

- 例（#124）: 「取得の担当になるのと打ち切りフラグを登録するのを同じロックでやる」「打ち切りは
  `Downloaded` として記録しない」「打ち切ったら `commit()` しない」はどれも `ModelDownloader` の
  中で繋いでいる部分にあり、部品（`write_verified` / `cancel_download`）のテストでは 1 つも
  捕まらなかった。
- 対策: **重い処理そのものを引数で受ける**（`acquire_and_transfer(spec, path, transfer)` /
  `verify_and_place(part, reader, …)`）。テストはネットワークにもディスクにも触らないフェイクを
  渡して、繋ぎの部分だけを決定的に検証できる。既存の `write_verified` が `impl Read` と
  `max_bytes` を引数で受けているのと同じ流儀。
- 継ぎ目を入れたら、下の「実装を壊してテストが落ちることを一度確かめる」を**繋ぎの側でも**やる。

## 縮退のテストは「症状が出る条件」まで再現する

縮退経路のテストは、条件を取り違えると**バグを入れ直しても緑のまま**になる。実装を壊して
テストが落ちることを一度確かめる（ミューテーション）。

- 例: 「手放したら位置が 0 に戻る」（#96）は、rodio がキューの中身をクリアする経路では
  rodio 側が 0 にするため、**キューが空**（終端まで再生した後）でないと症状が出ない。
  再生中に手放すテストだけでは、`position()` のガードを消しても落ちない。
- 終端到達を待つなら、フィクスチャを頭から流し切るのではなく**終端の手前へシークしてから**
  再生する（テスト時間を数百 ms に抑えられる）。

## ミューテーションを回す前にコミットする

壊して戻す手順は、たいてい `git checkout -- <file>` で戻す。**その 1 行が、まだコミットして
いない変更をまとめて消す**。#175 では、足したばかりのテストを 1 周目のミューテーションの
後始末が消し、以降の 4 件が「テストが無いから全部緑」を報告し続けた（穴が塞がったと
読み違える方向の嘘なので、たちが悪い）。同じ事故は #164・#165 でも起きている。

- **回す前にコミットする。** 戻し先があって初めて「戻す」が安全になる。
- 判定はビルドの成否と分けて読む。`test result` の行が出ないのは緑ではなく**ビルド失敗**。
  `cargo test --bin <name> 2>&1 | grep -q '^error\[E'` を先に見て、緑・落ちた・そもそも
  ビルドできない、の 3 つに分ける（`cargo test --lib` は bin クレートでは常に失敗する）。

## 繋いでいる関数は、呼べるなら丸ごと呼ぶ

「配線は、繋いでいる関数に継ぎ目を入れてテストする」の続き。継ぎ目を入れるのは、繋いでいる
関数が**テストから呼べないとき**の次善策で、呼べるなら**その関数ごと呼ぶ**ほうが確実に守れる
（継ぎ目を下げるたびに穴も 1 段下がる、という #178 の失敗が起きない）。

#175 の `refresh_detail_panes` は「ワーカーとウィンドウを触るから呼べない」ように見えて、
どちらもテストから作れた（`SummarizeWorker::start` / `TranscribeWorker::start` は
ジョブを投げなければスレッドが 1 本立つだけ、ウィンドウは `init_test_backend` で作れる）。
呼べるようにしたら、`stored` を定数へ書き換えて機能を丸ごと殺すミューテーションが落ちるように
なった。**「重そうだから呼べない」は確かめてから言う。**

## 継ぎ目を下げても穴は塞がらない——最初に「呼べる一番外側」を探す

指摘された 1 行を純関数へ切り出すと、その関数はテストで守れる。**しかし本番はその外側を
通っているので、穴は 1 段下がるだけ**。#182 では 3 周続けて同じことが起きた:

1. 読み取りの中の分岐 → `Fetch::classify` へ切り出す → **呼び出し側の写像**が無検査で残る
2. 写像 → `read_outcome_from` / `Summary::from_failure` へ切り出す → **結果をまとめる 1 行**が残る
3. まとめ → `count_search_result` へ切り出す → **控える 1 行**（`*stored.borrow_mut() = …`）が残る

3 のとき、その 1 行を消すだけで「読めなかったことを伝える」機能は画面から完全に消えるのに、
テストは 1 件も落ちなかった。**切り出すたびに、切り出した先はテストで守られ、その手前が
新しい穴になる。**

だから切り出す前に**「テストから丸ごと呼べる一番外側はどこか」を先に探す**。ウィンドウを
作れる（`init_test_backend` + `LibraryWindow::new()`）、ワーカーを立てられる
（`SummarizeWorker::start` はジョブを投げなければスレッド 1 本）、`&RefCell` / `&Cell` を
渡すだけ——このどれかに当てはまるなら、そこを呼ぶ。**「重そうだから呼べない」は確かめてから
言う**（`refresh_detail_panes` も `reset_search` も、呼べないように見えて呼べた）。

判定は**壊してから**やる。切り出した関数のテストが緑なのは当たり前で、確かめたいのは
「本番が通る 1 行を消したときに落ちるか」だけ。

## 状態を見分ける assert は、状態ごとに違う値に掛ける

`SummaryPane::NotesFromPartialTranscript` と `NotSummarized` は**見出しが同じ**（どちらも
「まだ議事録が無い」）。#175 では見出しで比べてしまい、警告が丸ごと消えるミューテーションが
素通りした。

assert 先は「その状態でしか出ない値」を選ぶ（本文・状態 enum そのもの）。**表示のどこかを
比べていれば守れている、とは限らない。**

## 支援技術に届いているかは、状態プロパティでは分からない

`accessible-checked` / `accessible-expanded` のような**状態**は、対になる宣言
（`accessible-checkable` / `accessible-expandable`）が無いと実際の支援技術には載らない。
ところが**テストバックエンドは状態プロパティを直読みする**ので、宣言が無くてもテストは通る。

だから状態を持つ部品のテストでは、状態そのものだけでなく**どう読まれるかの宣言**も見る
（`tests/ui_controls.rs` の `state_carrying_parts_declare_how_their_state_is_read`）。

## ガードは 1 箇所に集め、呼び出し側に二重に置かない

同じガードを本命と呼び出し側の両方に置くと、**本命を壊してもテストが落ちない**
（呼び出し側で止まってしまう）。#146 の `Select` では、`open-options()` のガードを外しても
`accessible-action-expand` 側のガードが効いてミューテーションが素通りした。

ガードは通り道 1 つに集める。そうすればテストがその 1 つを守る。

## 関数を使わなくしたら、その場で消す（差分ビルドでは気づけない）

呼び出しを別のものへ置き換えて元の関数が孤立しても、**手元の `cargo clippy` は差分ビルドなので
警告を出さないことがある**（そのファイルを再解析しないため）。CI はクリーンビルドなので
`-D warnings` で落ちる。#152 で実際に 2 件すり抜けた。

置き換えたら、その場で `grep` して呼び出しが残っているか確かめる。疑わしいときは
`find . -path ./target -prune -o -name '*.rs' -exec touch {} + && cargo clippy --workspace
--all-targets -- -D warnings` で解析し直す。**ディレクトリを列挙しない**——列挙するとモジュールが
増えたときに漏れる（実際 `src/windows` を足したときも、`src/summarize` を足したときも漏れた。
#187 でクレートが増えたときも、`find src` 決め打ちだったせいで `shoki-core/src` を取り落とした）。

なお**バージョン差による見逃しは別問題**で、そちらは `rust-toolchain.toml` が塞いでいる（#156。
手元と CI で同じ Rust を使う）。`touch` で解決するのは「同じバージョンでの差分ビルド」だけ。

`pub`（あるいは `pub(crate)`）だと dead_code の警告すら出ないので、可視性を下げる判断
（`docs/rules/coding-conventions.md`）とセットで効く。

## テストの期待値を検査しない

`assert!(!expected.contains(SEP))` のように、**テスト表に書いたリテラルへ assert を掛けても
何も守れない**。実装を何に書き換えても落ちない。#159 では「パスを混ぜない」という
`docs/rules/security.md` の保証をそう書いてしまい、レビューで「見ているように読めるが inert」と
指摘された（同じコミットで、本物の保証を固定していた assert を消してもいた）。

assert は**関数の出力**に掛ける。そして**保証を作っている場所で掛ける**——値を並べるだけの
関数にパス混入の検査をしても、そこはパスを作っていないので守りようがない。守れるのは名前を
作る側（`transcribe::audio_display_name` / `job_model_label`）だけ。

## 保証を消したら、その保証は消える

型を整理して不要になったフィールドを落とすとき、**そのフィールドを検査していたテストごと消す**
ことになる。フィールドは要らなくなっても、**保証は要る**ことがある。

#159 では `TranscribeState::Failed` からモデル名を落とした際、`job_model_label` の
「上書き指定はファイル名だけ」を固定していた唯一の assert が一緒に消えた。関数は健在で、
戻り値は別の経路（`Transcribing`）から画面に出続けていた。削除跡のコメントだけが残り、
「見ているつもりで何も見ていない」状態になっていた。

テストを消すときは、**それが何を守っていたか**を数え、まだ要るなら別の場所へ移す。

## 確認用バイナリに文言を複製しない

`examples/` で目視するのは**出荷される文言**でなければ意味がない。bin クレートなので `use` では
取り込めないが、`#[path]` でモジュールごと共有できる。

```rust
#[path = "../src/slint_map.rs"]
mod slint_map;
```

**文言そのものは共有クレートへ置くほうが強い**（#188）。`shoki-core` に移してからは、example は
`use shoki_core::…` と普通に書けるようになり、`#[path]` で取り込むのは Slint 型への写像
（`src/slint_map.rs`）だけになった——共有する量が 864 行から 95 行に減っている。`#[path]` が
残るのは `shoki` が bin だけのクレートで `use shoki::…` と書けないため。

#161 の時点で、複製していた `SUMMARY_QUEUED_LABEL` が実際にずれていた（`Waiting to summarize…`
と `Waiting to write notes…`）。**「あちらを変えたらここも合わせること」という約束は守られない。**

## 確認用バイナリでも、状態は 1 つの値から出す

`examples/` で状態を切り替えるとき、**状態 enum と、そこから出る表示を別々に選ばない**。
別々に選ぶと、本番では作れない組み合わせを目視してしまう。

#160 の時点で `transcript_view` は状態行を `has_transcript` から、空表示を `--transcribing`
フラグから別々に選んでいた。`--transcribing` を付けると、状態行は「Transcribed」なのに空表示は
「Transcribing — 48%」という、本番のどの経路でも作れない画面が出ていた。

状態の値（`TranscriptPane` など）を 1 つ作り、状態行も空表示もそこから導出する。
これは製品コード側の「状態 enum と説明を別々に組み立てない」（`docs/rules/slint.md`）と
同じ規律で、確認用バイナリだけ例外にすると、目視の対象が本番とずれる。

## テストが見ている入口と、本番が通る入口をずらさない

「重い処理を引数で受ける」継ぎ目を入れると、テストは**継ぎ目の内側**を呼ぶようになる。このとき
**本番だけが通る外側の 1 行**が残っていると、そこを剥がしてもテストは全部緑のまま通る。継ぎ目を
下げるたびに穴も 1 段下がるので、同じ指摘が何周も出る。

#178 では 3 周続けて同じ形になった:

1. `let _ = MaterializationOff::for_this_thread();` — 番人を束縛の書き方で即 drop できた
2. `list_sessions` から `without_downloads(...)` を剥がしても全テスト緑
3. 2 の修正が「番人を通らない双子」`scan_sessions_now` を作り、そちらを呼ぶ 1 行で全テスト緑

**守りたい処理を、守りの内側にしか書けない形にする**のが唯一の直し方だった:

- 番人は**呼び出し側に持たせず閉包で受ける**（`dataless::without_downloads`）
- 番人が**証（`dataless::NoDownloads` のような ZST。番人のモジュール外では構築できない）**を渡し、
  守られる処理がそれを引数で要求する。囲いの外から呼ぶ書き方がコンパイルを通らなくなる
- 証に `Send` / `Sync` を付けない（`PhantomData<*const ()>`）。スレッド単位の設定なら、子スレッドへ
  持ち込まれた時点で「囲いの中のつもりで効いていない」になる

**テスト用の継ぎ目そのものが穴になる**。#178 では「測り方を閉包で差し替えられる」形にしたせいで、
閉包の中に直接読み取りを書けば証の壁を素通りできた。**差し替えたいのが結果の扱いだけなら、
読み取りではなく結果の扱いを切り出す**（`recordings::apply_measured`）。

型で塞いだら、**既知の迂回を実際に当ててコンパイルが通らないことを確かめる**。テストを足す方向は、
継ぎ目を下げるたびに穴も下がるので収束しない。

## レビュー用のサブエージェントに、実装を書き換えさせない

観点別のレビューを並列で回すとき、エージェントが「壊して確かめる」を勝手に始めると、**その
書き換えが作業ツリーに残る**。#176 では 2 周目のエージェントが `transcribe_file` の分岐を
`let _ = (...)` へ潰し、テスト関数に `TEMP probe` を差し込んだまま終わった。こちらは指摘の
反映中だったので、危うくその状態をコミットするところだった。

- レビューの依頼文に「**ファイルを変更しない**」を明示する（読み取りと `cargo test` だけ）。
- それでも起きるので、**コミット前に `git diff` を目で通す**。`TEMP` / `probe` / `dbg!` /
  `let _ =` のような痕跡を grep するのは、その 1 段前の網。
- 痕跡を見つけたら、**部分的に直さず HEAD から戻してやり直す**。どこまで書き換えられたかを
  数え上げるより速く、確実。
